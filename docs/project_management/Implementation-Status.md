# Implementation Status

**Architecture baseline:** 0.3  
**Implementation plan:** 0.2  
**Current state:** SwiftPM protocol boundaries, image-domain state/storage ownership, typed function composition, policy validation, declarative operation/implementation contracts, both runtime registries with per-registration identities, registration-aware provider context creation, partial environment discovery, work/resource-access lease accounting, input-bound common qualification, initial scoped candidate ranking (including exact precision-support preferences), and a single-operation execution coordinator are implemented. The coordinator allocates the qualified output/temporary resource roles through the original provider context, validates request descriptors and provider-registration provenance, passes a role/access-indexed resource set to the exact implementation, reserves and revalidates the combined input/output/temporary access set, validates output-to-plane retention, and can publish an image revision through compare-and-swap. A single feasible memory domain is selected automatically; multiple feasible domains require an explicit per-role choice. Input import/remapping, physical capacity reservation/reuse, provider-verified residency/synchronization, whole-pipeline planning/cost, quality calibration, cancellation/device-loss recovery, and plugin/native releaser lifetime remain incomplete.

This file records actual repository state. The architecture and implementation plan remain normative for intended behavior; a listed design or deliverable is not considered complete merely because a related type exists.

## Implemented

### Swift package boundary

- Root SwiftPM package uses Swift language mode 6.
- Separate library products exist for GeneralExecutionProtocol, ImageProcessingProtocol, and ImageProcessingRuntime.
- ImageProcessingProtocol depends on GeneralExecutionProtocol; ImageProcessingRuntime depends on both; neither lower-level protocol depends on ImageProcessingRuntime.
- Core modules contain no Apple-framework or vendor-specific imports.

### ImageProcessingRuntime foundation

- A separate ImageProcessingRuntime SwiftPM product depends on GeneralExecutionProtocol and ImageProcessingProtocol.
- Actor-backed OperationImplementationRegistry stores implementations by implementation identifier plus implementation version; exact duplicate registrations are rejected and distinct versions may coexist.
- Registration validates the implementation specification against its associated operation's static specification before storing it.
- Private type-erased entries preserve the associated implementation type in a checked async dispatch closure; operation and input values are downcast at the boundary, and output type identity is checked.
- Registered metadata and statically compatible candidates can be enumerated in deterministic order by operation specification or concrete operation step; this does not rank candidates or inspect the provider environment.
- Each implementation and provider registration receives a unique registration identifier in addition to its stable identity. Environment snapshots carry provider registration identities. Qualified candidates carry the exact operation step, typed input, implementation and provider registration identities, execution target, and prepared context. Runtime dispatch consumes the candidate as a unit and rejects removed/replaced registrations rather than silently dispatching a new implementation/provider under the same key.
- Actor-backed ExecutionProviderRegistry independently stores selected provider packages by provider identifier and rejects duplicate registrations. It passes the generated registration identifier into context creation, revalidates the same registration after the asynchronous context factory returns, and rejects an optional registration-bound context that reports another identity.
- Provider discovery assembles an ExecutionEnvironmentSnapshot from provider/device descriptors and state observations. Partial failures are retained alongside the snapshot; failed observations are represented as unknown rather than available or zero load.
- Provider/device ownership violations and duplicate device identifiers are reported as structured provider contract failures; a provider with no discovered devices remains valid for opaque managed execution.
- RuntimeWorkLedger atomically tracks per-target reserved/submitted work and exact generic resource-access reservations. Read-only reservations may coexist; any write/read-write access is exclusive. Multi-resource acquisition is all-or-nothing, current bindings must be revalidated before a resource-bearing lease can be submitted, and retained handles are released only on pre-submit cancellation or observed completion.
- OperationExecutionCoordinator executes one already-qualified candidate without selecting or reranking it. It pins the provider instance, allocates every qualified output/temporary role through the original context, validates each returned handle against the selected memory domain, request, target, and exact provider registration, then exposes the resources by role and declared access mode to the implementation. It reserves and revalidates the complete declared input/output/temporary access set before dispatch. Every allocated output resource must occur in exactly one produced layer's plane binding; temporary resources must not occur in the returned image storage bindings. A singleton feasible memory domain is unambiguous; multiple choices require an explicit per-role selection. The lease is released only after the implementation completion boundary. In-place updates still use the exact qualified source revision and Image compare-and-swap. Input import/remapping and multi-step planning remain outside this slice.
- ImageOperationImplementation.execute is the completion boundary for runtime input leases: implementations must await provider work that can still access declared input resources before returning or throwing.
- RuntimeEnvironmentSnapshotCoordinator composes provider discovery with runtime-owned workload state into uniquely identified snapshots with monotonically increasing generations.
- Provider-reported queue/load observations remain separate from runtime-owned reserved/submitted counts.
- CommonQualificationResolver accepts the actual typed OperationValue. It verifies the operation's concrete Swift input and operation types against the registered implementation, not only their stable type identifiers. A pixel-backed device-local input resource must also carry the exact provider registration identifier captured by the candidate's environment; same-target resources created by another registration or lacking provenance are rejected.
- ImageOperationInputValue supplies an explicit mapping from logical input indices to exact ImageStateSnapshot revisions and explicit layer/composite targets. It never infers a layer from visibility, order, or first-match rules. Generic non-image values can instead conform to OperationResourceInputValue and describe their own generic ExecutionResource bindings.
- Input qualification checks accepted operation/implementation layer kinds, actual pixel layout/interpretation/channel order/subsampling/sample origin/color/scientific metadata, input storage component precision, and each required bound resource's kind/capacity/alignment/memory domain/access mode/target compatibility. For pixel-backed composite inputs, every referenced layer and every plane resource must be bound; a partially bound composite is rejected rather than qualified from the resources that happened to be present.
- Candidate dispatch consumes the operation step, input value, registered implementation descriptor, target, and context captured by qualification. A registration removed or replaced after qualification produces a structured stale-registration failure; it cannot silently substitute an implementation with the same key.
- Qualified candidates retain the exact environment snapshot identifier plus the provider/device state snapshots used during evaluation. Each telemetry metric exposes a known/stale/unknown assessment at the resolver's evaluation time using its own observedAt/validUntil interval; source and quality metadata remain available unchanged. Unknown or stale optional telemetry does not invalidate an otherwise eligible candidate, and a reported zero remains a known zero.
- ImageOperation may derive a typed, invocation-specific resource plan from its exact input and immutable parameters. The plan describes both output and temporary slots. The resolver requires exact role matching with implementation resource requirements and combines data-derived capacity/alignment with implementation kind, allowed domains, and access mode. After context preparation, each output/temporary resource kind must be advertised by the context, and the candidate's allocatable domains are the intersection of the implementation's allowed domains and the context's advertised memory domains. These capabilities describe support, not free capacity or a reservation; no resource is allocated at qualification time.
- Image-producing operation values conform to ImageOperationOutputValue and expose an ImageOperationOutputDescriptor containing the exact immutable ImageStateSnapshot (document plus revision-matched ImageStorageBindingSet) and explicit produced/replaced layer references. Every produced pixel layer must have a storage binding in that snapshot. The returned value therefore retains its output resource handles for its own lifetime; output storage is no longer detached from the image revision. Post-dispatch validation checks layer kind, pixel representation, output precision, clip/normalize range metadata, and typed operation postconditions. Preserved document layers are not treated as produced output.
- Resource-access reservations are runtime-owned and generic. They do not allocate resources, reserve provider memory capacity, establish residency, or prove that a provider can still execute after device loss. Immutable ImageStateSnapshot values retain their revision-matched storage bindings; replacing the current image state does not release resources still held by older snapshots or submissions.
- The evaluate API remains the hard-eligibility operation and never ranks. The resolve API orders only qualified candidates: low latency uses pairwise dominance over shared fresh provider/device queue-delay, implementation fixed-overhead, and bound-input staging components. Bound-input staging is known zero only when every distinct declared input handle is device-local on the exact candidate target and carries the same provider registration identifier; legacy/unattributed or prior-registration handles remain unknown. Low memory compares the sum of per-role minimum planned output/temporary resource capacities; existing persistent input allocations are not charged again. Deterministic-results preferences compare the implementation's declared determinism. Preference priority is processed from higher to lower, weights scale pairwise win rates, and stable implementation/provider/device identity breaks unresolved ties. Cost components retain units, source/quality/timestamps, and estimated/stale/unknown state. Unmodeled path costs remain explicitly unknown. Resource memory-domain options are exposed per role without allocation or domain selection.
- Full-path costs (cross-target/cross-registration import and remapping, host/device staging, conversion, allocation latency, compute, synchronization, output materialization, energy, and throughput), source-quality weighting/calibration and refresh policy, pipeline sequence planning, and execution remain incomplete. Resource provenance prevents direct qualification of a device-local handle from another registration, but the runtime does not yet import/remap such resources. Provider context and resource-handle retention through plugin unload/device loss is not yet a complete coordinator-owned lifecycle.

### GeneralExecutionProtocol foundation

- Stable provider, device, and capability identifiers.
- Semantic version and half-open version-range types.
- Generic provider/device capability values and declarative capability requirements.
- Capability requirements identify whether a feature must be reported by the provider, device, either, or the created execution context.
- Standard generic capability identifiers cover resource kinds, allocation/import, work submission/dependencies, synchronization, and peer transfer.
- Execution contexts expose context-local capabilities; optional context protocol conformance remains the executable contract. Resource-producing providers can receive the exact runtime registration identifier during context creation; registration-bound contexts can report it for validation.
- Provider and device descriptors.
- Provider-level and device-level availability/load snapshots.
- Dynamic observations explicitly distinguish known, stale, and unknown values. Known observations require a validity interval and source.
- An opaque execution-context contract and provider/device discovery contracts.
- Generic resource identifiers, target-scoped resource references, validated resource descriptors/requests, and allocation/import capability contracts.
- Resource access declarations with reference-counted handle semantics; imported handles retain their source.
- Typed work submission and completion contracts, dependency declarations, cancellation outcomes, and optional synchronization capability.
- Environment snapshots validate provider/device ownership and duplicate identities.
- A provider can represent an opaque managed execution target without exposing a device list.
- Structured ExecutionProviderFailure values carry provider/target identity, machine-readable failure kind, advisory recovery guidance, and optional native code/message diagnostics.
- Test-only ExecutionProviderConformanceHarness validates provider/device ownership and duplicate IDs, visible and opaque targets, context-target identity, truthful optional capability claims, allocation/import descriptors, typed submission, and synchronization.

### ImageProcessingProtocol foundation

- Stable operation, implementation, parameter, option, and typed value identifiers.
- Typed operation values and associated input/output types; typed and erased operation specifications preserve the same semantic data.
- Named immutable operation parameter schemas and instance values, with required/optional entries, typed domains, duplicate/unknown/missing-value checks, and finite numeric bounds.
- Operation specifications declare independent input-storage, computation, accumulation, and output-storage precision domains. Storage component types and arithmetic precision are distinct types.
- Numerical contracts declare rounding, overflow, output-range behavior, determinism, and optional absolute/relative error tolerances.
- Effect contracts separate required operation effects from effects permitted to implementations, and separately state input-mutation and output-aliasing semantics.
- Layer contracts declare accepted and produced layer kinds. Pixel-backed raster/mask/label-map operations must declare input/output pixel representation domains; annotation-only operations do not invent pixel-storage constraints.
- Pixel representation domains describe layout, color/scientific interpretation, color model, alpha, transfer function, color-space identity, channel roles/order, subsampling, sample origins, and measurement units.
- One generic ImageOperationImplementation protocol, specialized by its associated operation type; the protocol has no per-implementation qualification hook.
- ImplementationSpecification statically validates operation identity/version/value types, parameter support subsets, precision support subsets, numerical guarantees, determinism, effects/mutation/aliasing, layer/pixel representation subsets, resource requirements, capability declarations, and optional cost hints.
- Implementation resource requirements declare input/output/temporary roles, generic resource kind, allowed memory domains, minimum capacity/alignment, access mode, and import requirements. Performance hints remain static estimates, not live load.
- Operation-instance preflight validates whether parameter values are legal for the operation. A value outside one implementation's narrower support rejects that candidate without invalidating the operation instance.
- Typed ImageFunction<Input,Output> sequential composition, typed identity function, direct operation append, and heterogeneous ordered step storage.
- OperationStepIdentifier identifies each step occurrence; reused right-hand functions are reidentified on composition while source identifiers remain available.
- Immutable QualificationPolicy keeps hard requirements separate from soft optimization objectives and scopes declarations to the pipeline or a concrete step occurrence.
- Policy validation checks provider/precision set intersections over effective scopes, execution-capability type contradictions, same-scope preference conflicts, invalid weights, step identity, and precision applicability.
- Step-scoped policy declarations are rebased when a right-hand function is composed and its step occurrences receive new identifiers.

### ImageProcessingProtocol image semantics

- Image and layer identifiers, with layer identity scoped to an image through LayerReference.
- Monotonic ImageRevision with explicit overflow detection.
- Immutable ImageDocumentSnapshot with canvas extent, ordered typed layers, duplicate-ID validation, foreign-reference rejection, and layer-to-canvas extent validation.
- LayerSpatialMapping with a checked invertible 4x4 affine map from layer sample-centre indices to canvas sample-centre indices. Same-grid layers use identity; different extents require an explicit map.
- Raster, mask, label-map, and annotation content descriptors with distinct semantic validation.
- PixelDataDescriptor with component precision, channel identities/roles, explicit color channel models (gray, RGB, YCbCr, custom), scientific interpretation, alpha mode, and optional channel value ranges.
- PixelStorageBinding assigns every pixel plane exactly once to one or more generic execution resources; it supports one shared allocation or separate per-plane allocations, validates each resource capacity, and retains all handles.
- ImageStorageBindingSet associates plane storage with layer references for one exact ImageIdentifier/ImageRevision, verifies descriptor identity, and reports unbound layers without rejecting non-resident document content.
- Image is a thread-safe reference-type state owner; synchronous snapshots pair immutable document state with its exact binding set.
- Image can adopt an already-prepared ImageStateSnapshot without rebuilding storage bindings. Image.replace can build a candidate from descriptors/bindings or atomically publish a prepared snapshot after validating image identity, exact next revision, and compare-and-swap. Stale concurrent replacements fail explicitly.
- Interleaved and planar storage planes with byte offsets, row/pixel/slice strides, subsampling, explicit per-plane sample origin/chroma siting, required power-of-two base/row/slice alignment, plane-to-layer coordinate conversion, channel mappings, checked minimum-capacity computation, and overflow rejection.
- Mask semantics (binary, coverage, probability), integer label identifiers, and explicit annotation coordinate spaces.

## Not implemented

- Non-affine spatial deformation fields and calibrated world-coordinate transform model.
- Concrete provider implementations of resource allocation/import/export, residency transitions, eviction policy, and safe native release. The GEP descriptor and resource reference can now carry provider-registration provenance, and Phase 5 rejects a device-local input whose registration does not match the candidate. Providers must implement the registration-aware context overload and stamp created handles; legacy/external resources with no provenance cannot prove same-registration residency. This still does not observe eviction, external memory pressure, native-handle invalidation, or device loss.
- Provider conformance tests proving resource retention through asynchronous work, cancellation, device loss, and failure.
- Provider-backed physical memory-capacity reservation, resource allocation/reuse, complete residency/import feasibility, and external-memory pressure accounting. RuntimeWorkLedger coordinates access to already-bound handles; it does not reserve physical memory or guarantee that a provider will keep a resource resident against external pressure.
- Source-quality weighting and telemetry refresh policy for available-memory/queue/load evidence. Fresh queue-delay observations can now participate in pairwise low-latency ranking, and each component preserves source, quality, and validity metadata; source quality is not yet assigned a numeric confidence weight, and stale/unknown observations do not rank.
- Provider-verified output residency, synchronization, and numerical pixel-content validation that cannot be proven from descriptor metadata alone. The current single-operation coordinator validates allocation request descriptors and provider-registration provenance and checks that output-role handles are retained by produced plane bindings; this does not prove the device has not evicted or invalidated the allocation.
- Physical capacity reservation/reuse, provider memory-pressure and eviction policy, input import/remapping, and allocation-failure re-resolution. The coordinator now asks the qualified context to allocate output/temporary roles and validates the returned descriptors, but a successful allocation call is not a separately modeled physical-capacity reservation or a guarantee of future residency.
- Reference-counted retention of an unregistered implementation package until all outstanding candidates are released. Candidates fail closed when their registration is removed/replaced.
- Complete end-to-end cost estimation. The initial ranker covers pairwise queue-delay/fixed-overhead comparisons, declared determinism, exact precision-support preferences, per-invocation minimum planned output/temporary capacity, and descriptor-based input residency. It can establish zero bound-input staging for distinct declared handles already device-local on the exact target; this is not a measured transfer duration or a guarantee for unrepresented inputs. Non-local/cross-target routes, conversion, allocation/context latency, compute, synchronization, output residency/materialization, energy, and throughput remain unavailable.
- Whole-pipeline planning and lifecycle recovery around the single-operation coordinator: reservation refresh/re-resolution, explicit input import/remapping, cancellation/timeouts/device loss, diagnostics, and transactional multi-step publication.
- CPU provider and numerical reference image operations.
- Metal, CUDA, OpenCL, Direct3D 12, Vulkan, OpenCV, Core Image, Accelerate, or model-runtime implementation packs.

## Next implementation order

1. Extend Phase 5 ranking without changing eligibility: model explicit host/device and device/device transfer/import routes, conversion, allocation/context latency, compute, synchronization, output residency/materialization, and pipeline-segment transitions. Preserve the rule that only distinct declared input handles already device-local on the exact target and same provider registration receive a zero bound-input staging estimate; all other routes remain unknown until evidenced. Add source-quality/refresh semantics without inventing confidence values. Precision-support preferences now rank candidates, but the execution contract still needs an explicit rule for carrying a hard-required or preferred mode into an implementation that declares multiple modes. Keep energy/throughput unknown until calibrated models exist. Do not allocate for every candidate merely to probe feasibility.
2. Continue Phase 6 from the implemented single-operation allocation path. Add explicit input import/remapping with source-handle retention and verified synchronization; then implement allocation-failure/re-resolution policy, cancellation/timeouts/device loss, and provider/native releaser retirement without weakening original hard constraints. Preserve the existing order: pin the exact provider, allocate the qualified output/temporary roles, reserve and revalidate the complete declared access set, dispatch and await the implementation completion boundary, validate output, then publish by compare-and-swap. Output ImageStateSnapshot values own their exact storage bindings for as long as the revision is retained; temporary resources remain invocation-scoped through completion. Do not add a separate global GPU cache. Add sequence planning only after this lifecycle is complete.
3. Add a CPU provider and a small numerical reference operation as the first end-to-end vertical slice after the runtime lifecycle is correct; then add GPU and managed-runtime adapters independently.
